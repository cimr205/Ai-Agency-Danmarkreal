## What was fixed
- **Two real authorization holes**: `customer-portal` (opens Stripe's billing portal — can cancel the subscription, change payment method) and `create-checkout` (starts a new subscription) had **no role check at all**. Any company member — `employee`, `readonly`, anyone — could call either. Added an `is_company_admin()` check to both (reusing the same Postgres function the RLS policies already use), matching "only Owner or authorized administrator may change the subscription."
- **Silent, unreviewed billing change**: `check-subscription` — a function polled by the frontend every 60 seconds, by any logged-in company member — would, when a trial was within 3 days of ending, silently call `stripe.subscriptions.update()` to change the billed quantity to match the current active-user count. That means any employee's routine page load could change what the company gets charged, with zero owner approval and no audit trail. Changed it to **report** the mismatch (`seat_mismatch: { activeUsers, purchasedSeats }`) instead of acting on it; the actual update now only happens via an explicit `confirm_seat_sync` request, re-checked server-side for `is_company_admin`.
- **No webhook for the actual SaaS subscription.** `stripe-payment-webhook` exists, but it's scoped to a *different* feature (AI Agency Danmark's customers paying their own invoices via `invoice_payment_reference` metadata) and explicitly ignores everything else. There was nothing durably syncing subscription status/cancellation/payment-failure from Stripe — the system relied entirely on `check-subscription` happening to be called. Added `stripe-subscription-webhook` (new function, not deployed) handling `checkout.session.completed` (subscription mode), `customer.subscription.updated`, `customer.subscription.deleted`, and `invoice.payment_failed`. Reuses the existing `provider_webhook_receipts` table (unique on `(provider, external_event_id)`) for idempotency and `sendCriticalAlert` for failures — same pattern as `stripe-payment-webhook`, per "reuse the existing architecture." Every handler re-fetches the subscription live from Stripe before writing, rather than trusting the embedded webhook payload, so a reordered/delayed delivery can't regress already-synced state.
- **Stripe return flow was a dead end.** `create-checkout`'s `success_url`/`cancel_url` point back into the app with `?subscription=success|cancelled`, but nothing ever read that param — Dashboard now shows a toast and strips the param. Separately, `Onboarding.tsx`'s "already has a company" redirect guard was dropping the query string entirely (`<Navigate to=".../dashboard" />` with no search), so the cancel confirmation could never have reached Dashboard even after adding the toast — fixed to forward `location.search`.
- **Checkout/portal opened in a new tab** (`window.open(..., '_blank')`) while their return URLs target the *same* app — the original tab (and its subscription state) never updated, and the new tab's "success" landing was easy to miss. Changed both to same-tab navigation (`window.location.href`), consistent with how the onboarding wizard already does it.
- **Billing portal return URL was hardcoded to `/en/`** regardless of the user's actual locale. Now takes `locale` in the request body (same pattern as `create-checkout`).
- **Subscription page didn't show seat count at all** ("Vis antal betalte brugerpladser" from the spec). Now shows purchased seats, and — for admins only — the seat-mismatch banner with an explicit confirm button described above.

## Explicitly not built
- **No new trial or discount model** — per "implement only the approved business model," the 3-day trial (already set in phase 1 of this run) and the existing full-suite/per-module pricing structure are unchanged in substance, only in correctness/authorization.
- **No seat-reduction policy decision** (what happens to existing users when the paid seat count goes down) — the spec asks to "define" this, but that's a product policy call with real consequences for someone's team access, not a code bug to fix unilaterally. Flagging it as an open decision rather than inventing one.
- **Did not deploy anything.** `stripe-subscription-webhook` is written but not registered in Stripe (needs a webhook endpoint configured there, pointing at this function, with its own signing secret as `STRIPE_SUBSCRIPTION_WEBHOOK_SECRET`) and not deployed to Supabase. The two role-check fixes and the portal/checkout changes are also undeployed — committed to the working branch only.
